# Change note: spec v0.6, gaps G19–G22 and the Gate 1 R5 cutoffs

**Date:** 2026-10-14
**Document:** `01-event-semantics.md` (v0.5 → v0.6)
**Decided by:** Steven: G19–G22 accepted as provisionally implemented; R5 cutoffs are daily
**Status:** committed locally on `spec-v0.4-fixtures`, **not pushed** (Steven is reviewing locally first)

## Why

Writing the reference calculation exposed four more places where the spec was silent (`changes/2026-10-14-reference-calculation.md`). Separately, §8 required R5 to match for September without naming any cutoffs. The reference already behaves this way, so **no code changed**. The spec now says what the code does.

## Changes by section

| Section | Gap | Now says |
|---|---|---|
| §1 registry | G20 | `unreadable` = no *complete* line decoded; partial bytes are discarded and not counted as Q1 |
| §1 registry | G21 | non-gzip bytes after a complete gzip member → `truncated` |
| §2 Q3 | G22 | strict form `YYYY-MM-DDTHH:MM:SS[.f{1,6}](Z\|±HH:MM)`: uppercase `T` and `Z`, at most 6 fractional digits, no `:60` |
| §2 | G19 | `type`, `public` and `payload` are checked for presence only; a non-string `type` is stored as its JSON text and flagged `unrecognized_type` |
| §8 criterion 2 | R5 cutoffs | 24 daily cutoffs at 00:00Z, 2026-09-08 → 2026-10-01; every 7-day window lies inside September |
| §9 | — | new row recording the R5 cutoff decision |

## Effects

- **§1 and §2 only. §3 and §4 are unchanged.** Gate 1 hasn't run, so nothing needs re-running.
- **The pipeline author** (a different agent, per §6) must implement G19–G22 from the spec alone.
- **Fixture coverage:** none of G19–G22 has a fixture yet. All of them were probed directly against the reference (see the reference change note). Candidates for later fixtures.
- **The Gate 1 run command** must pass the 24 cutoffs, e.g. `--cutoff 2026-09-08T00:00:00Z … --cutoff 2026-10-01T00:00:00Z`.
