# Spec 03 v0.3: S14, burst-and-die positives

**Why:** Steven asked for S14 on 2026-10-16. The panel's hackathon point exposed a gap.
- A hackathon or classroom repo gains many new contributors at once, then dies. That fits V1's target exactly.
- The single-author filter (S8) doesn't catch it, because these repos have many authors.

**What (03 §4.4, §7.3, §9):**
- **Retention:** the share of a positive's new contributors still contributing in `[t + 30d, t + 60d)`, frozen at `t_R = t + 60d + 1h + L`. Below 0.2, the positive is "burst-and-die".
- **A diagnostic only:** it uses data after the label window, so it can never be a feature, a filter or a label input (§6).
- **Reported:** per cutoff and model, as `burst_and_die_top100` in `eval.csv`, for cutoffs whose `t_R` falls inside the backfill.
- **Pre-registered decision:** if more than 25% of `M1`'s or `M2`'s top-100 positives are burst-and-die on the **training** cutoffs, a filter using only data as of `t` is decided before any test cutoff is scored. This keeps the pass bar (S11) honest.

**Effect on the backfill:** none. The last training cutoff (2026-06-22) has its `t_R` (2026-08-21) inside 2026-03-01 → 2026-10-01. Later cutoffs report the diagnostic only where data reaches.
